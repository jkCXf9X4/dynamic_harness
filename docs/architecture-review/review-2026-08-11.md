# Codebase Review — 2026-08-11

> Complete, critical review of the Dynamic Harness codebase.
> Scope: `src/dynamic_harness/*`, `tests/*`, core docs. All 201 tests pass (`pytest`).
> Focus: architectural solutions, module/class boundaries, and pattern alternatives.
> Bias: understandability and ease of working over cleverness; large changes are allowed — this is experimental software.

---

## 0. Executive summary

The architecture is sound at the high level — actor-style agents, runtime-owned task graph,
artifact-driven handoff, a plugin tool registry, mechanical context management, and a
deterministic benchmark harness are all real strengths. The gaps are mostly at the *boundaries*:
**private fields are accessed across module boundaries everywhere**, **environment truth is
hardcoded into the agent core**, **parts of the runtime are silently race-prone under the parallel
delegation the system explicitly promotes**, and **TLS verification is disabled by default** in two
of the three entry points.

Ordered work list (details in §7):

| # | Area | Severity |
|---|------|----------|
| 1 | Fix `environment_info` — it lies about the runtime and leaks experiment state into the agent core (§3.1) | High |
| 2 | Harden `deliver_report`/`Repository` against concurrent child commits (§3.2) | High |
| 3 | Enable TLS verification by default (§3.3) | High |
| 4 | Replace cross-module private-field access with a real tool/agent interface (§3.4) | High |
| 5 | Stop appending a growing context observation per turn (§3.5) | Medium |
| 6 | Isolate event-handler failures from the agent loop; single source for event text (§3.6) | Medium |
| 7 | Apply `token_limit` *inside* tools, not after full execution (§3.7) | Medium |
| 8 | Fix `webfetch` SSRF/size gaps (§3.8) | Medium |
| 9 | Close `bash` global-lock granularity; sandbox inconsistencies (§3.9–3.11) | Low |
| 10 | Re-sync onboarding docs (`AGENTS.md`, `docs/api/tools.md`) with the current layout (§4.5) | Low |
| 11 | Collapse Agent's 18 forwarding properties and extract a testable run-loop (§4.1) | Medium |
| 12 | Unify outcome extraction (`AgentRunner` + `MetricsCollector` reach into `_last_report`) (§4.3) | Medium |

## 2. Strengths (worth keeping)

1. **Tool infrastructure is clean.** `ToolDef` + schema-driven registry with a single
   `register_default_tools()` seam (`core/tools/registration.py`) and one schema emitter
   (`openai_schemas`, `registry.py:65`) is the best boundary in the codebase. Adding a tool is one module + two register lines.
2. **Security posture of the filesystem tools is thoughtful.** `resolve_safe_path` sandboxing
   (`filesystem.py:83`), hidden-file filtering, and per-path write locks are real wins.
3. **Context management is genuinely separate.** `AgentContext` owns all turn/prune/restore/compress
   invariants; the run loop and tools both use it without touching each other's fields.
4. **CLI was thoughtfully re-layered.** `present.py` (view-models), `render.py` (engine adapters),
   `format_event.py` (single event→text source) eliminate the historical TUI/Rich duplication.
   This is the right shape; keep it.
5. **Safety invariants are concrete and testable** : max iterations, repeated-call detection,
   wall-clock timeout, prune/restore/compress (all covered in `tests/backend/test_agent_loop*`,
   `test_capabilities.py`, `test_tool_interaction.py`).
6. **Benchmark harness is the right idea.** Deterministic verifiers + weighted objective scoring
   (`benchmark/scoring.py`) instead of LLM self-ranking is a genuine methodological upgrade.
7. **Good naming and small files overall.** Median file is well under 200 LOC; only `agent.py`,
   `tui.py`, `context.py` are large.

## 3. Findings — High priority

### 3.1 `Agent.environment_info` hardcodes environment truth into the agent core

`core/agent.py:140-150`:

```python
@property
def environment_info(self) -> str:
    return (
        "[Environment]\n"
        "Python 3.11 | pip NOT available | pytest NOT installed\n"
        "Working dir: project root with pyproject.toml\n"
        "Packages: pydantic, openai, dotenv, pyyaml, httpx, rich, textual, pathspec\n"
        ".optimize_benchmarks/ exists — do not recreate\n"
        "Git available | os: linux\n"
        "Do NOT attempt to install packages — use python3 -c for inline code\n"
    )
```

Problems:

- **It states facts that are false in the real runtime.** This machine is Python **3.10**, and the
  bundled `venv` **has pytest installed**. The agent is told *the opposite*.
- **It leaks benchmark-run specifics into the core agent.** `.optimize_benchmarks/ exists — do not
  recreate` and "pytest NOT installed" are artifacts of *one* experimentation setup, yet every agent
  in every environment is prompted with them. This is precisely the kind of unknown that poisons
  prompt-quality experiments — the benchmark optimizes a prompt that half-asserts figures about an
  environment an agent never sees.
- **The same block is duplicated** in `core/agent_system_prompt.txt:51-68` ("Working Environment —
  pre-provisioned, do NOT install"). Two copies that will drift (they already disagree: the `.txt`
  says Python 3.11 available as `python3`; the property says the same but both are wrong here). It is
  also re-emitted inside every context observation (`agent.py:339`), i.e. repeatedly per turn.

**Fix direction:** the environment must be *injected data*, not source code. Add a small
`EnvironmentInfo` value (python version, working dir, packages, available commands, notes) derived
from the runtime at construction and passed into the agent (via Runtime config plumb). The `.txt`
system prompt should stop asserting environment specifics and refer to the observation block instead.
This removes the "unknowns that influence perceived quality" the review brief warns about.

### 3.2 Concurrent child `report()` can corrupt the repository (race)

The system's core behavior is *parallel delegation* (`agent.py:412-414`, `_gather_deferred_and_finalize`
uses `asyncio.gather`). Each finishing child calls `report()` → `Runtime.deliver_report()`
(`runtime.py:138-174`), which **synchronously** does:

1. `artifact_store.save(artifact)` — writes `artifact.json`
2. `repository.commit(commit)` — writes the child's `commit.json`, then for each parent:
   `parent.child_ids.append(child.id)` and `_save(parent)` (`repository.py:49-58`) — rewrites the
   **same parent `commit.json`**.

Two children reporting at once both mutate the shared `Commit` for the parent and both `write_text`
the same file. Under interleaving, one write wins and the other is silently lost → **provenance
gaps** (parent loses a `child_ids` link on disk). There is no lock around `deliver_report`. The only
lock that exists is `repo_lock`, acquired solely inside the *bash tool* (`process.py:36-39`).

**Fix direction:** make the repository commit operation atomic for a task-tree — either serialize all
`deliver_report`/`commit` mutations with `repo_lock` (hold a single lock around artifact save +
commit + parent update), or compute child linkage in a single unbatched write. An
`async def deliver_report` awaited by `Agent.report` (making it `async`) is also the correct API
shape anyway (see §5-B) since it performs real I/O on the event loop today.

### 3.3 TLS verification disabled by default

`cli/common.py:69` and `api/harness.py:87` construct `OpenAIProvider(..., verify_ssl=False)` while
`OpenAIProvider` defaults to `True` (`llm/openai_provider.py:26`), and `benchmark/run.py:79` also
forwards `False`. Every default launch sends the API key over the channel **without certificate
verification**. The correct default is `verify_ssl=True`; opting out should require an explicit
config/flag.

### 3.4 Cross-module private-field access makes the "actor model" aspirational

The documentation (AGENTS.md, VISION.md) promises strict encapsulation. In practice the boundaries
are porous, all in the "convenient but brittle" direction:

| Accessor | Access target |
|---|---|
| `core/tools/agents.py:155-161` | `agent._runtime`, `agent._deferred_delegates`, `agent._format_delegate_result` |
| `core/tools/agents.py:206` (converse) | `target._messages` |
| `core/tools/agents.py:215` (read_artifact) | `agent._artifact_store` |
| `core/tools/context.py:77` | `agent._messages` |
| `core/runner.py:38-44` | `root._last_report`, `root._last_failure` |
| `benchmark/metrics.py:105-106` | `agent._messages`, `agent._iteration` |
| `agent.py:248-270` (itself) | `child._runtime`, `child._last_report`, `child._last_failure` |

Every one of these is a private-name dependency between modules that should communicate through an
interface. Consequences: any refactor of Agent internals (e.g. replacing `_deferred_delegates`) breaks
7 call sites in 3 modules; tests depend on the same privates (`test_capabilities.py:235`,
`test_tool_interaction.py:546`).

**Fix direction:**

- **Tool boundary.** Tools today receive the whole `Agent`. Introduce a narrow `ToolContext` façade the
  tool host passes instead: `llm`, `messages_view`, `artifact_store`, `delegate()`, `report()`,
  `emit_activity()`, `generated_root`, `workspace_lock`, `gitignore_filter`, and the context-primitive
  methods. Tools stop reaching into `agent._*`. This is the single highest-value change for
  maintainability.
- **Outcome boundary.** Add a readonly public `AgentOutcome` (report | failure | escalation) on Agent
  and have `AgentRunner.run()` return it; have `MetricsCollector` consume it. Removes the
  runner/metrics private reads.
- Keep the public surface small but *formal*, even if it stays duck-typed.

## 4. Findings — Medium

### 4.1 `Agent` (623 LOC) conflates four jobs; the proxy wall should go

`agent.py` is the biggest file and the densest. It mixes:

1. **Orchestration API** — `delegate`, `report`, `escalate`, `fail`, `continue_with_input`,
   `get_other_agent` (fine, small);
2. **The run loop** — `_run_loop`, `_handle_tool_calls`, `_gather_deferred_and_finalize`,
   `_llm_call_with_retry`, `_check_repeated_calls`, `_safety_check` (~250 LOC — the hardest logic to
   test, with nearly all edge cases covered only via chewy mock-LLM scripted tests);
3. **Formatting glue** — `_format_delegate_result`, `_context_observation`,
   `_emit_iteration/_emit_llm_end` that re-derive event data shapes that also exist in
   `format_event.py`/`harness.py`;
4. **18 forwarding property proxies** — `_turn_counter`, `_turn_order`, `_turns`, `_pruned`,
   `_prune_markers`, `_in_flight_prune`, `_messages` getter/setter, `active_turn_ids`,
   `evict_pruned_overflow`, … (`agent.py:98-128`). Several are used *only by tests*
   (`_turn_order`, `_turns`, `_prune_markers`, `_in_flight_prune`).

**Fix direction:** follow the already-established pattern (state in `AgentContext`, tools in
`core/tools/`): extract a `RunLoop` (or `AgentLoop`) class that owns safety, the observation block,
retry, tool dispatch, and repeated-call detection, receiving a bounded interface to `Agent`. The
proxies collapse because loop and tools then talk to `context`/`ToolContext` directly. Tests move
from scripting a mock LLM to unit-testing `RunLoop` pieces.

### 4.2 Context observation is appended every turn and grows quadratically

`_run_loop` (`agent.py:509`) appends a fresh `{"role": "system", "content": obs}` for every iteration,
and the observation itself (`_context_observation`, `agent.py:313-340`) rebuilds a summary of *all*
active turns plus the full `environment_info`. Over a 20-turn agent:

- the conversation carries ~20 stale observation blocks totaling O(n²) event-summary text;
- each block repeats the full environment text + task description.

Since prune/compress target *turns* (assistant+tool), the observation messages themselves are never
dropped. This works against the very premise of bounded context.

**Fix direction:** keep **one** observation slot: replace the previous observation message in place
before each LLM call (the last message is the observation), so it never accumulates. Cheap, big
token win, no behavior change.

### 4.3 `AgentRunner` and `MetricsCollector` duplicate outcome extraction

`AgentRunner` (`runner.py:38-44`) reads `root._last_report/_last_failure`; `MetricsCollector`
(`metrics.py:102-112`) iterates agents reading `agent._messages/_iteration`. Both exist to derive
"what happened" from the mesh. Merge into one outcome model (`§3.4` Outcome) so the CLI, the API, and
the benchmark derive from a single source.

### 4.4 Event plumbing is triplicated and not failure-isolated

- **Formatting lives in 3 places** with distinct date-shape assumptions: `emit_*` builders in
  `agent.py` (`_emit_llm_end`…), formatters in `cli/format_event.py`, and a *third* hand-rolled
  formatter in `api/harness.py:_on_activity:106-139`. `harness.py` should call `format_event()`.
  Today, a new event type or renamed key silently breaks one consumer.
- **Handler failure kills the agent.** `Runtime.deliver_report` fires `event_bus.emit_report`
  (`runtime.py:174`) with no try/except; `Agent.report` is synchronous and called from the run loop
  (`tools/agents.py:164-174`). A raising handler (e.g. a TUI lambda mid-teardown) propagates into
  `_handle_tool_calls` → `run()`'s `except Exception` → the agent is force-failed for a UI bug.
- **`format_event` doesn't cover all SAFETY_WARNING subtypes.** `agent.py` emits `timeout` and
  `agent_error` warnings (lines 288, 401); `format_event.py:62-66` only renders `max_iterations` and
  `repeated_calls` → CLI users silently miss timeout/agent-error warnings.

### 4.5 Stale onboarding docs

`AGENTS.md` and `docs/api/tools.md` still describe the pre-restructure layout:

- `AGENTS.md:19,55,186,255` reference `core/capabilities.py`, `core/protocols.py`,
  `register_default_tools()` in `capabilities.py`, and test files `tests/test_agent.py` /
  `test_capabilities.py` — none of which exist (all split into `core/tools/*` and `tests/backend/*`).
- The AGENTS.md "Conventions" section says "New tools are registered via `register_default_tools()` in
  `capabilities.py`" — it is `core/tools/registration.py`.

Because AGENTS.md is the first thing an agent reads, this directly degrades onboarding quality
("unknowns that influence perceived quality"). **Fix:** regenerate the directory map,
`api_modules`, tests table, and tool-section pointers from the real tree.

### 4.6 `token_limit` is applied *after* tools execute fully

`ToolRegistry.execute` (`registry.py:40-63`) pops `token_limit`/`token_offset` and truncates only the
*returned string*. But `read` reads the whole file, `grep` scans the entire tree, `bash` runs the
command, `webfetch` downloads the full page, `write` writes blindly — all before truncation. So
`token_limit=20` doesn't bound upstream work at all; worst case the truncated content cost is a poor
proxy for the real work done. The two-stage cap (`registry` truncation + `agent.py:432-438`
`MAX_TOOL_RESULT_CHARS`) is redundant.

**Fix direction:** pass `token_limit` (and a byte cap) into the tools that materialize large content
(`read`, `webfetch`), and honor a results size cap in `webfetch` regardless.

### 4.7 `webfetch` SSRF and size gaps

`core/tools/network.py:28-51` checks only that the **literal hostname** is not a literal private IP;
a DNS name resolving to an internal address passes, and redirects aren't re-checked. There is no
response-size limit (a 100 MB page is fully fetched into memory before being truncated downstream).

**Fix direction:** fetch with `follow_redirects=False` and validate/walk each hop; allow a resolved-IP
check (resolve + verify) via httpx's proxy/connection or a pre-resolution; cap response bytes.

### 4.8 `ask` is unsupported in the TUI

`cli/terminal.py` installs a Rich `ask` (via `_install_ask_tool`, line 46), but **`cli/tui.py` never
does**. In TUI mode the default `ask` falls back to the blocking `input()` (`tools/agents.py:189`) on
the threadpool — a raw stdin prompt that bypasses the TUI entirely. Either wire a TUI `ask` message,
or make the default `ask` return a structured "no TUI input available" so the agent escalates instead
of hanging on invisible stdin.

### 4.9 Coarse `bash` global serialization and sandbox/gitignore inconsistency

- `process.py:36-39`: *every* bash command (including read-only `git status`/`ls`) takes the global
  `repo_lock`, serializing all agent processes. A per-repo lock is only needed for mutating commands;
  treat `git`/`rm`/builds as mutating, run reads unlocked.
- `resolve_safe_path` sandboxes `read/write/edit` to `generated_root`, but `glob` (`filesystem.py:131`)
  and `grep` walk `Path.cwd()` with only gitignore/hidden filtering. In the benchmark flow the two
  disagree (cwd changes), so "sandboxed" reads and "unbounded" globs point at different trees. Make
  the sandbox the single source for every path-typed tool.

### 4.10 `Runtime.delegate` trusts `Task.parent_id` over the `parent` argument

`agent.delegate` builds `Task(parent_id=self.task.id)` and passes `parent=self`; `Runtime.delegate`
(`runtime.py:110-136`) uses the task's embedded `parent_id` (via `deliver_report` →
`commit_ids_for_tasks([agent.task.parent_id])`, `runtime.py:168-170`) rather than the actual `parent`
object passed in. A custom agent could forge parent linkage, breaking the provenance story. Set
`task.parent_id = parent.id` inside `Runtime.delegate` and stop trusting the caller.

## 5. Architectural alternatives considered

### A. ToolContext façade (agent → tool boundary) — *recommended*
Instead of passing `Agent` to every tool fn (`registry.execute(name, id, agent=..., **kw)`), the host
builds a small `ToolContext` (runtime services + agent surface) once and the registry passes that.
Benefits: tools become pure about *what they need*; tests create a fake context in ~5 lines instead of
`runtime._agents[id] = agent`; the `agent._*` access list in §3.4 disappears. Cost: one adapter type,
one call-site change. This is the single most impactful refactor for "ease of working".

### B. Make the delivery pipeline async
`report()` is sync (`agent.py:603`), yet `deliver_report` does several disk writes and fires handlers.
In TUI/CLI these runs on the loop; handler exceptions can fail the agent (§4.4). An `async report()` +
`await runtime.deliver_report()` keeps I/O and handler dispatch explicitly off the happy path and
dovetails with §3.2 locking. (Compatible substitution for the tool functions, which are already async.)

### C. AgentOutcome instead of `_last_report` reach-in
Rather than `AgentRunner`/`MetricsCollector`/`format_delegate_result` reading `_last_report`,
`_last_failure`, and iterating `_messages`, have the loop produce a `RunSummary` (reports, failures,
per-agent usage/turns) the runtime retains. Every consumer (CLI, API, benchmark, parent formatting)
reads one well-defined object. Low risk, removes the ugliest private reads.

### D. Inject `EnvironmentInfo` instead of hardcoding (see §3.1)
Keep the observation block (it is good for agents to see budget/context) but source its content from
a runtime-provided description assembled from the real environment, and emit it once, not per turn.

### E. Single observation slot (see §4.2)
Replace-in-place the trailing observation message before each LLM call. No new concepts, big token
savings.

### F. Event refinement
- Move all event-data construction into one place (the emit sites already use `data: dict`; add one
  helper per event type, or thin payload Pydantic models), and make `format_event.py` the only
  formatter (delete the `harness._on_activity` duplicate).
- Wrap handler dispatch in `try/except` in `EventBus` so a UI/logger bug cannot fail an agent.
- Cover `timeout`/`agent_error` in `format_event`.

### G. God-object services
`Agent.__init__` pulls 8 collaborators off `runtime` (`agent.py:69-76`: event_bus, tool_registry,
usage_tracker, provider, trace_store, artifact_store, generated_root). Consider a single
`RuntimeServices` (frozen dataclass) handed to Agent as one argument — less plumbing, shows the
dependency graph at a glance. Optional polish; keep the current behavior.

### H. Consider abandoning the double truncation
`registry`'s token_limit slicing (registry.py) + `agent.py`'s `MAX_TOOL_RESULT_CHARS` cap implement the
same idea twice with different units. Keep the registry-level `token_limit*4` char budget (it already
emits an excellent "use token_offset to see more" hint) and let the agent cap be the fallback ceiling;
document the difference or merge into one policy object.

## 6. Module/class sizing and abstraction read

| Unit | LOC | Verdict |
|---|---|---|
| `core/agent.py` | 623 | Too big, 4 jobs, 18 proxies → split (§4.1) |
| `cli/tui.py` | 368 | Acceptable; already slimmer after `present.py` extraction. Watch it. |
| `core/context.py` | 342 | Good single responsibility; prune rebuild is O(n) per call — fine at expected scale |

| Everything else | <190 | Good |

Abstraction levels are currently *heavy on plumbing, light on interfaces*: lots of private-field
reach-across (§3.4) instead of small formal interfaces. Moving to the ToolContext/Outcome model makes
the design *easier*, not harder, to hold in one's head — matching the review brief's bias for plain,
understandable structures (the `present.py`/`render.py` split is the proof it works).

## 7. Proposed order of work (sequenced)

1. **Correctness/security first, small diffs:**
   1. `verify_ssl` default → `True` everywhere; explicit opt-out flag in config/CLI.
   2. Wrap `deliver_report`'s artifact+commit+parent-update in the repo lock (or make it async +
      atomic); add a targeted concurrent-child test.
   3. Sandbox the `glob`/`grep` path sources to match `resolve_safe_path`.
   4. `Runtime.delegate` sets `task.parent_id` from `parent`.
2. **De-risk the agent loop (biggest test surface):**
   5. Extract `RunLoop` from `Agent`; collapse the proxy wall.
   6. Single observation slot; `EnvironmentInfo` injected instead of hardcoded; drop the duplicated
      env table from `agent_system_prompt.txt`.
   7. `try/except` in `EventBus` handlers; route `harness._on_activity` through `format_event`;
      render `timeout`/`agent_error`.
3. **Boundary hardening (highest ROI for working ease):**
   8. Introduce `ToolContext` passed to tools; remove `agent._*` accesses (tools, runner, metrics).
   9. Introduce `AgentOutcome`; `AgentRunner` and `MetricsCollector` consume it.
4. **Tools & integration:**
   10. Pass `token_limit`/byte-cap into `read`/`webfetch`; cap `webfetch` size; re-validate redirects.
   11. TUI `ask` support (or structured "no input" fallback).
   12. Narrow `repo_lock` to mutating bash commands only.
5. **Docs sync (cheap, high onboarding value):**
   13. Regenerate `AGENTS.md` map + `docs/api/tools.md`; fix tool-count/registration pointers.
