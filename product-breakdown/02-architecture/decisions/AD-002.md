# AD-002: Collaboration Group = Children of a Common Parent, Explicit Membership, Default-Deny

## Status
Accepted

## Layer
Architecture

## Context
Enabling peer collaboration (option B, sibling mailbox) violates the
actor-model context-encapsulation invariant ("know only parent + children +
task"). To contain that violation, the collaboration group must be bounded and
authorized. The runtime already tracks parentage (`task.parent_id`, the task
graph), so "children of one parent" is a concept with zero new structural
entities.

Documented in:
- `product-breakdown/02-architecture/multi-agent-coordination/INVESTIGATION.md`
  §"Deep dive: B — sibling collaboration under a common parent" and
  §"Requirements for B-curated" (REQ-1, REQ-2).
- `product-breakdown/02-architecture/multi-agent-coordination/collaboration-setting-spec.md`
  (the advanced-layer spec; AC-1..11 hold as policy-layer acceptance).

**Rationale basis:** DOCUMENTED — REQ-1/REQ-2 are stated explicitly with
theory citations (Hackman: real team; Project Aristotle: structure & clarity;
TMS directory; bounded rationality).

## Decision
A collaboration group is defined as **children of a common parent, with
explicit membership** (REQ-1). Peer messaging is **default-deny**: a pair may
communicate only if the parent introduced it — at delegation time via
`collaborate_with=[...]`, or mid-run via `introduce(agent_a, agent_b, note)`
(REQ-2). The permission is an *edge*, not a global right, enforced in
`get_other_agent` / a policy object. The parent is the group's natural
authority: it can authorize, observe, and revoke channels.

## Alternatives Considered
- **Unconstrained B (any agent may message any agent)** — REJECTED: re-opens
  unbounded cross-branch contamination and needs a global permission system.
- **A (parent-mediated relaying)** — REJECTED (AD-001): parent becomes a
  bottleneck and its context rots.
- **C (team/panel with chair)** — considered; converges with B-curated once
  introductions exist; the channel decision (AD-003) picks the hybrid.

## Consequences
**Positive:**
- Contamination is confined to a trusted sibling set that shares a coordinator;
  no global graph addressing, so other subtrees are never touched.
- No new permission subsystem: scope collapses to "same parent", and the parent
  is the existing authority.
- Cycles are bounded to a small, known edge set (the subtree); per-pair
  counters make loop detection tractable (REQ-9).
- Introductions are requestable and declinable (REQ-3) — psychological safety
  preserved; a child may decline with no penalty.

**Negative:**
- The isolation invariant is still softened for the group (bounded + authorized,
  but softened) — group-internal contamination remains possible; mitigated by
  summary-only delivery, per-recipient caps, and the parent's final VERIFY.
- Adverse sibling data is possible: one child can mislead another; each child
  retains autonomy (a sibling message is input, not authority — REQ-12).
- Channels must close when the parent settles or is killed; settled siblings
  are read-only targets (REQ-10).
