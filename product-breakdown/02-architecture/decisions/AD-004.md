# AD-004: Facilitation = Mechanical Policy Layer + Sparse Parent Arbitration, No Facilitator Agent

## Status
Accepted

## Layer
Architecture

## Context
Question: should the collaboration channel have a **facilitator** to mitigate
negative effects, or stay **pure child-to-child**? The theory resolves this as
a three-layer stack in which the "facilitator" is almost entirely *mechanical
structure*, with a *sparse* arbitration role only at conflict. The sharpest
anchor is Elinor Ostrom's commons governance (Nobel 2009, *Governing the
Commons*, 1990): long-lived shared-resource groups thrive through explicit
institutional design — mechanisms, not a person.

Documented in:
- `product-breakdown/02-architecture/multi-agent-coordination/INVESTIGATION.md`
  §"Facilitation layer: facilitation yes, facilitator agent no".
- `product-breakdown/02-architecture/multi-agent-coordination/management-theory-communication-facilitation.md`
  (facilitator literature: Doyle, Bens, Kaner — content-neutral, "contributes
  structure and process").

**Rationale basis:** DOCUMENTED — the three-layer recommendation and the
rejection of a facilitator agent are stated explicitly with Ostrom's design
principles cited.

## Decision
Facilitation is a **three-layer stack with no facilitator agent**:

- **L0 — Pure peer-to-peer (steady state).** Workspace reads/writes + bounded
  message channel, direct child↔child, parent absent. Covers ~all routine
  coordination. The "context over control" default.
- **L1 — Mechanical facilitation (the invisible facilitator).** All policy/code,
  zero LLM tokens, no bottleneck: boundaries/membership (REQ-1/2, Ostrom #1);
  monitoring via append-only writes + provenance (Ostrom #4, "monitors are the
  users"); graduated sanctions (REQ-6 caps, REQ-9 loop detection — warn →
  tighten → hard stop → notify, Ostrom #5); round/cadence; write-conflict
  conventions.
- **L2 — Sparse arbitration (the low-cost local arena).** The only *agent*
  facilitation, existing solely for conflicts L0/L1 cannot resolve: child↔child
  negotiate over the rich channel first; an *unresolved* dispute escalates once
  to the **parent**, who arbitrates once and is done (arbitrate, converse,
  disconnect, or dissolve the group). This is Ostrom #6 + Netflix "step in at
  risk points" + Hackman coaching-at-transitions (REQ-8, REQ-14).

## Alternatives Considered
- **Pure child-to-child with zero facilitation** — REJECTED: the
  commons-tragedy trap — no monitoring, no graduated sanctions, no conflict
  resolution; exactly the churn/contention risks that motivated the guardrails.
- **An always-on facilitator agent** — REJECTED: repeats option A's cost model
  (burns tokens on every interaction), duplicates what policy already does
  better, violates content-neutrality, and becomes a single point of failure
  and lifecycle burden.
- **A dedicated facilitator agent for very large groups (edge case)** — NOT
  adopted as default: a content-neutral sibling "chair" is a defensible
  *optional* enhancement only when the parent is saturated; must be scoped to
  L2-style arbitration and parent-overridable. Default: don't build it.

## Consequences
**Positive:**
- Sustainable self-governance without a boss: Ostrom's design principles are
  enacted as code (rules/caps/provenance), not as a person.
- Zero-token facilitation: L1 is policy, so the "facilitator" adds no LLM cost
  and no bottleneck.
- Conflict resolution is low-cost and local: one escalation to the parent, who
  already holds authority (a peer-chair agent would need to defer to it anyway).
- REQ-13 (graduated sanctions) and REQ-14 (conflict-resolution arena) are
  directly realized; REQ-15 (distributed monitoring) via append-only committed
  workspace writes.

**Negative:**
- The parent is awakened for risk-point events (new connection, over-budget,
  escalation, child lacking context — REQ-8); if the parent later starts
  reading exchange *content* to "help", it decays back into the rejected
  option A — enforced by design (content is pull-only, oversight is one event
  line).
- L1's mechanical rules (caps, sanctions, cadence) must be specified as policy
  objects — the workspace mechanics and round/cadence semantics are still open
  (IMP-002).
